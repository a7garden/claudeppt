# 서명된 승인 기록이 서버 없이 정본을 정한다

된다. 다만 「정본」의 뜻이 바뀐다. 서버가 정해 주는 하나의 main 이 아니라, **명부에 적힌 승인자의 ed25519 서명이 이어진 승인 기록을 각 앱이 자기 사본에서 검증해 계산한 결과**가 정본이 된다. 이것은 Radicle 이 이미 운영 중인 모양이다. 위임자 서명 수로 정본 ref 를 각 노드가 스스로 계산하고, 권한 문서는 「parent = 현재」 선형 체인에 과반 수락으로만 넘긴다 ([Canonical References in Radicle](https://radicle.garden/blog/canonical-references-in-radicle), [radicle cob/identity.rs](https://docs.rs/crate/radicle/0.24.0/source/src/cob/identity.rs)). ClaudePPT 는 재료를 거의 다 갖췄다. 앱마다 DPAPI 로 싼 iroh ed25519 열쇠가 있고 iroh-base 1.5.0 의 `SecretKey::sign` · `PublicKey::verify` 로 새 암호 의존성 없이 서명 · 검증이 된다. 판 관리(작업 사본 · 3방향 얹기 · 보류 갈래 · 가지 합치기 · 사본 가져오기)도 git CLI 로 이미 있다 ([vcs.rs](../../src-tauri/src/vcs.rs), [branch.rs](../../src-tauri/src/branch.rs)). 대가는 셋이다. 첫째, **「담당 쪽만 보이기」는 전체 사본 구조에서 지킬 수 없다.** 지금은 덱 주인 서버가 보내지 않는 것으로 지키는데([collab.rs:409-432](../../src-tauri/src/collab.rs)), 사본을 주는 순간 모든 쪽과 전 이력이 넘어간다. 둘째, **모두가 꺼져 있으면 어떤 기술로도 변경은 그 PC 안에 갇힌다.** 남는 수단은 서명된 증분 묶음 파일을 메신저 · 공유 폴더로 넘기는 것과, 끄기 전에 「아직 아무에게도 안 간 변경」을 크게 알리는 것뿐이다. 셋째, 협업 서버 · 러너 · 원격 화면 계층 약 3,000줄을 걷거나 고치고 새 코드 2,000~3,000줄을 써야 한다(추정). 추천은 **git 객체는 그대로 두고, 줄기 밖 별도 ref 에 서명된 승인 기록 체인을 쌓고, iroh 위에는 fetch 전용 `git upload-pack` 만 여는 설계**이며, 담당 쪽만 볼 사람은 지금의 호스트 모드로 계속 들이는 혼합 구조다.

## Radicle 이 답을, Upwelling 이 함정을 보여 준다

서버 없이 「승인된 것만 정본」을 소프트웨어로 강제한 운영 사례는 사실상 Radicle 하나다. 노드는 자기 ref 가 바뀔 때마다 모든 ref 목록에 서명해 `refs/rad/sigrefs` 에 두고, 누구든 최초 신원 문서에서 출발해 갱신을 인증할 수 있다. 검증 모델은 TUF 에서 왔다 ([Radicle Protocol Guide](https://radicle.dev/guides/protocol)). 정본 브랜치는 위치가 아니라 **신원 문서의 threshold 만큼 위임자가 같은 커밋을 가리키는지**로 정해지고, 노드는 자기 로컬에 있는 각 투표자 사본만 보고 표를 센다. 투표자들이 한 줄 이력 위에 있으면 지지가 충분한 가장 앞선 커밋이 이기고, **진짜로 갈라지면 정족수가 없어 ref 는 이전 값에 머문다** ([Canonical References in Radicle](https://radicle.garden/blog/canonical-references-in-radicle)). 신원 문서 변경은 정본 규칙의 threshold 와 무관하게 늘 위임자 과반이 필요하다. revision 은 parent 가 현재 문서여야 하고, 하나가 수락되면 나머지 열린 revision 은 모두 Stale 이 된다. 이미 수락된 revision 에 대한 동시 거부는 「알 길이 없었다」며 버린다 ([radicle cob/identity.rs](https://docs.rs/crate/radicle/0.24.0/source/src/cob/identity.rs)). 즉 권한 변경은 **현재 문서 위의 compare-and-swap 체인**이다. ClaudePPT 가 가져올 핵심이 바로 이 둘(서명된 ref 목록, CAS 로만 넘어가는 권한 문서)이다.

Radicle 의 약점도 그대로 배울 거리다. 기기마다 DID 가 따로라 여러 기기에서 쓰려면 기기 열쇠를 각각 위임자로 더해야 하고, 열쇠 분실 복구 절차는 가이드에 없다 ([Radicle User Guide](https://radicle.dev/guides/user)). 비공개 저장소도 **저장 데이터를 암호화하지 않고** 허용 목록으로만 복제를 제한한다 ([Radicle Protocol Guide](https://radicle.dev/guides/protocol)). 실제로는 상시 켜진 seed 에 기댄다. 사용자 후기는 정본 규칙을 「JSON 안의 또 다른 ACL 언어」라 「흥미롭고도 무섭다」고 적었다 ([Notes on radicle](https://equalsraf.codeberg.page/articles/2026-02-08-notes-on-radicle.html)). threshold 1 에서 두 위임자가 조상 관계 없는 커밋을 가리킬 때 Radicle 이 무엇을 하는지는 1차 자료로 확인하지 못했다. 이 경우가 ClaudePPT 의 기본 상황(승인자 아무나 한 명이 넣는다)이므로 규칙을 직접 정해야 한다.

Ink & Switch 의 Upwelling 은 반대 방향의 교훈이다. draft 마다 목적 제목을 달고, 하나가 병합되면 열린 draft 들에 rebase 해 충돌을 병합 전에 드러내는 UX 는 좋다. 그러나 편집자 승인은 소프트웨어가 강제하지 않는 사회적 관례로 두었고, **동시 병합을 막지 않았으며 막으려면 서버나 커스텀 CRDT 가 필요하다**고 스스로 적었다 ([Upwelling](https://www.inkandswitch.com/upwelling/)). 승인 게이트를 강제하려면 이 「동시 병합」 문제를 결정적 규칙으로 풀어야 한다는 뜻이다. 그 규칙의 본보기는 Matrix state resolution v2 다. 권한 이벤트를 보낸 사람 권한 순, 시각, ID 순으로 정렬해 하나씩 auth-check 하므로 모든 서버가 같은 결론에 닿는다. 다만 서버들이 상태를 다르게 보다가 갈라질 수 있다고 명시한다 ([Matrix spec rooms v2](https://spec.matrix.org/v1.16/rooms/v2/)). git-bug 는 벽시계를 표시용으로만 쓰고 Lamport clock 과 해시 사전순으로 순서를 정하며, clock 이 DAG 와 어긋나는 커밋은 버린다 ([git-bug data model](https://github.com/git-bug/git-bug/blob/master/doc/design/data-model.md)). 신원 쪽에서는 Keyhive 의 「사람 = 자기 기기들을 멤버로 둔 그룹」 모델이 ClaudePPT 의 「앱마다 열쇠」와 정확히 맞는다. 기기를 잃으면 남은 기기가 그 열쇠만 뺀다 ([Keyhive notebook](https://www.inkandswitch.com/keyhive/notebook/)). Keyhive 자체는 pre-alpha 이고 감사받지 않았으며 동시 상호 취소는 미뤄 둔 문제라 의존성으로는 쓰지 않는다 ([Keyhive 01](https://www.inkandswitch.com/keyhive/notebook/01/), [Keyhive 04](https://www.inkandswitch.com/keyhive/notebook/04/)). gitsign 은 공개 투명성 로그(Rekor)에 기록해야 해서 서버 없음 조건과 맞지 않는다 ([gitsign README](https://raw.githubusercontent.com/sigstore/gitsign/main/README.md)).

## iroh 위에는 fetch 전용 upload-pack 하나만 연다

주고받기는 새로 발명할 것이 없다. git remote helper 의 `connect` 는 양방향 전이중 연결 하나 위에 원격의 `git upload-pack` 을 붙여 git 고유의 pack 협상을 그대로 쓴다 ([gitremote-helpers](https://git-scm.com/docs/gitremote-helpers)). Radicle 도 stream 위에서 응답 쪽은 upload-pack 을 돌리고 가져오는 쪽은 gix-protocol 로 v2 협상을 한다 ([radicle-fetch transport.rs](https://docs.rs/crate/radicle-fetch/0.18.0/source/src/transport.rs), [radicle-node worker.rs](https://docs.rs/radicle-node/0.11.0/src/radicle_node/worker.rs.html)). ClaudePPT 는 이미 git CLI 를 부르므로, **새 ALPN `claudeppt/git/1` 을 더하고 들어온 bi 흐름을 `git upload-pack <덱 저장소>` 의 stdin/stdout 에 잇는** 방식이 가장 싸다. 지금 `p2p::serve` 가 bi 흐름을 협업 포트 TCP 로 잇는 `pipe` 와 같은 꼴이고([p2p.rs:87-122](../../src-tauri/src/p2p.rs)), 시험 `pipes_a_tcp_connection_through_iroh` 를 틀로 다시 쓸 수 있다. 엔드포인트 `Builder::alpns` 로 받을 ALPN 을 여럿 정하고 `Builder::hooks` 로 연결 설정 단계에서 거절할 수 있다 ([iroh Builder](https://docs.rs/iroh/latest/iroh/endpoint/struct.Builder.html)). gix 는 fetch 클라이언트는 쓸 만하지만 서버 쪽과 push 는 「아직 plumbing 이 필요한」 목록에 있어 지금 고를 이유가 없다 ([gitoxide crate-status](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md)). iroh 위 git 선행 구현 둘(cmars/git-remote-iroh, wronex/iroh-git)은 실험 단계이고 각각 비밀키 평문 저장 · 저장소 단위 권한 · 크기 제한 없음이라 구조 참고용으로만 본다 ([cmars/git-remote-iroh](https://codeberg.org/cmars/git-remote-iroh), [wronex/iroh-git](https://github.com/wronex/iroh-git)).

**receive-pack 은 열지 않는다.** 모두가 완전 사본을 갖는 구조에서는 각자 상대에게서 fetch 만 하면 된다. 상대의 ref 는 `refs/cppt/peers/<열쇠>/*` 같은 격리 이름공간에 받고, 검증을 통과한 승인 기록만 로컬 `main` 을 fast-forward 시킨다. 이렇게 하면 「남이 내 ref 를 덮어쓰는」 공격면이 통째로 없어지고, 받는 쪽 검증이 유일한 관문이 된다. 연결을 받을 때는 원격 EndpointId 를 그 덱 명부와 비교하고, 요청 첫 줄의 덱 ID 가 그 열쇠에 허용된 덱인지 한 번 더 보며, upload-pack 에 넘길 경로는 덱 ID 로 앱이 정한다. 동시 upload-pack 수와 응답 크기에 상한을 두고, 이미 꺼 둔 훅(`core.hooksPath=.git/claudeppt-no-hooks`, [vcs.rs:21-41](../../src-tauri/src/vcs.rs))은 반드시 유지한다. 지금 `vcs_fork_fetch` 가 하는 「이력이 이어지지 않으면 버림」 검사(`merge-base`, [branch.rs:388-406](../../src-tauri/src/branch.rs))도 그대로 쓴다.

피어 찾기는 iroh 가 해 주지 않는다. pkarr/DNS 와 mDNS 는 **열쇠를 이미 알 때 주소를 찾아 줄 뿐**이다 ([iroh discovery](https://docs.iroh.computer/concepts/discovery)). 그래서 명부(열쇠 · 이름 · 권한)를 덱 저장소 안 서명된 ref 로 두고, 초대 티켓으로 처음 한 번만 「덱 ID + 초대한 사람 주소」를 건넨다. 그 뒤로는 명부의 열쇠마다 주소를 찾아 온라인인 누구에게서든 받는다. 「새 커밋이 생겼다」 알림은 iroh-gossip 을 곁들일 수 있지만 0.x crate 이고 bootstrap 피어가 필요하므로 ([iroh-gossip](https://docs.rs/iroh-gossip/latest/iroh_gossip/)) 정본 경로는 git fetch 로 두고 알림은 깨져도 되는 보조로 둔다. iroh-docs 는 같은 키를 여럿이 쓰면 타임스탬프 기준 last-writer-wins 이고 3방향 합치기가 없어 git 을 대신할 수 없다 ([iroh-docs](https://github.com/n0-computer/iroh-docs)).

크기는 따져 둘 문제다. 이 PC 에서 잰 덱 9개 중 새로 만든 덱은 전체 약 4MB 지만, **가져온 PPTX 59쪽 덱은 `.git` 만 약 222MB, 작업 트리 포함 448~604MB** 이고 그 대부분이 `source/` 원본 쪽 그림과 `assets/` 다(코드 조사 노트의 `du` 실측). n0 공개 릴레이는 공식적으로 개발 · 취미용이고 SLA 가 없으며 한도를 공개하지 않는다 ([public relays](https://docs.iroh.computer/iroh-services/relays/public)). n0 는 직접 연결이 「약 10 중 9」라고 주장하고 데이터의 95% 가 직접 흐르는 것이 흔하다고 쓰지만 독립 측정은 없고, libp2p 의 대규모 독립 측정은 약 70% 였다 ([holepunching](https://docs.iroh.computer/concepts/holepunching), [iroh 1.0](https://iroh.computer/blog/v1), [arXiv 2510.27500](https://arxiv.org/html/2510.27500v1)). 증분 fetch 는 KB 단위라 문제없지만 **첫 사본은 릴레이 경유면 오래 걸린다.** 그래서 `source/pages/*.png` 는 줄기 판에서 빼 지연 받기로 돌리고, 첫 사본은 LAN(mDNS) 이나 `.cppt` 파일로 건네는 길을 기본으로 둔다. 유료 Shared relay(Pro 월 $19, 5MB/s, 릴레이 egress 100GB, 직접 트래픽은 세지 않음)로 옮길 수 있게 릴레이 URL 설정은 열어 둔다 ([shared relays](https://docs.iroh.computer/iroh-services/relays/shared)).

## 승인은 줄기 밖 서명 체인에, 권한은 CAS 명부에 둔다

서명을 git 객체 안에 넣는 길은 모두 어색하다. 커밋 트레일러는 자기 해시를 서명할 수 없고 승인은 커밋 뒤에 생긴다. git 내장 ssh 서명은 열쇠를 파일 · 에이전트로 git 에 내놓아야 해 DPAPI 보관과 부딪치고, 지금 일부러 끈 `commit.gpgsign=false` · `log.showSignature=false`(판 목록 파서를 깨서 껐다, [vcs.rs:29-36](../../src-tauri/src/vcs.rs))를 되살려야 한다. git notes 는 승인의 순서를 담기 어렵다. 그래서 **별도 ref `refs/cppt/trunk` 에 작은 승인 기록 파일을 커밋으로 쌓는다.** 기록 하나는 「덱 ID, 줄기 순번 n, 새 줄기 커밋 X 와 그 트리 해시, 앞 줄기 커밋 W, 앞 기록 해시, 승인한 제안 id, 승인자 열쇠, 그 승인자가 본 명부 판 해시, 시각(표시용)」을 canonical JSON 으로 담고 그 바이트에 `SecretKey::sign` 한 서명을 붙인다. 앞 기록 해시를 묶으므로 되감기 · 끼워 넣기 · 재생이 검증에서 걸리고, 로컬 `main` 은 이 체인의 마지막 X 를 가리키는 **결과로만** 움직인다. 서명 함수는 iroh-base 1.5.0 이 `SecretKey::sign(&self, msg) -> Signature`(src/key.rs:323) 와 `PublicKey::verify`(src/key.rs:134) 로 이미 내놓으므로 `p2p.key`([p2p.rs:45-62](../../src-tauri/src/p2p.rs))를 그대로 쓴다. 제안(PR)은 지금의 가지 · 보류 갈래(`cppt/sian/` · `cppt/hold/`, [branch.rs:1-44](../../src-tauri/src/branch.rs))를 `refs/cppt/proposals/<작성자 열쇠>/<id>` 로 옮긴 것이고, 승인은 지금의 `merge_into`(`merge --no-ff`, 겹치면 abort 후 겹친 파일 보고, [branch.rs:183-219](../../src-tauri/src/branch.rs))를 돌린 결과에 기록 하나를 서명해 붙이는 일이다.

명부는 Radicle 신원 문서를 따라 **`refs/cppt/roster` 의 선형 CAS 체인**으로 둔다. 덱을 만든 열쇠가 창세 명부에 서명하고, 각 판은 「사람 → 기기 열쇠들 · 이름 · 권한(승인 · 편집 · 의견 · 보기) · 담당 쪽」과 승인 threshold 를 담는다. 명부를 바꾸는 판은 parent 가 현재 판이어야 하고, **현재 명부의 승인자 과반 서명**이 모여야 효력이 난다. 하나가 수락되면 같은 parent 의 다른 열린 판은 낡음(Stale)이 된다. 담당표(`assign.json`)도 판 밖 파일에서 이 명부로 옮긴다. 담당이 이제 승인 검증의 입력이 되기 때문이다. 지금 `invite.rs` 의 「같은 이름이면 권한을 잇는다」([invite.rs:151-163](../../src-tauri/src/invite.rs))는 서명 신원에서는 아무것도 보증하지 못하므로 버린다.

**권한 박탈**은 승인 기록에 묶인 명부 판 해시로 판정한다. 기록은 「그 기록이 참조한 명부 판에서 승인자였고, 그 판이 그 시점 체인의 현재 판이었을 때」만 유효하다. 명부에서 빠진 사람이 오프라인에서 계속 서명해도, 새 명부 판을 받은 피어는 낡은 명부를 참조한 새 기록을 거절한다. 남는 구멍은 백데이트다. 빠진 사람이 박탈 소식을 못 받은 척 옛 명부를 참조해 서명할 수 있다. Keyhive 도 미해결로 둔 문제이고 ([Keyhive 01](https://www.inkandswitch.com/keyhive/notebook/01/)), Matrix 처럼 권한 이벤트를 먼저 적용하는 규칙으로 줄인다. 피어는 명부 체인을 먼저 최신으로 맞춘 뒤, 박탈 판보다 인과적으로 앞서지 않은(그 판의 앞 줄기 커밋 위에 쌓이지 않은) 그 사람의 기록을 무효로 본다. 이미 받은 사본은 회수할 수 없다는 점도 분명히 한다. 내보내기의 뜻이 「연결 끊기」에서 「앞으로의 줄기를 주지 않음」으로 약해진다.

**동시 승인**이 이 설계의 가장 어려운 곳이다. 승인자 둘이 같은 줄기 W 위에서 서로 다른 제안을 승인하면 `refs/cppt/trunk` 에 순번 n 기록이 둘 생긴다. Radicle 식 「갈라지면 멈춘다」는 안전하지만, threshold 1 인 작은 팀에서는 사소한 경쟁마다 줄기가 서 버린다. 그래서 결정적 승자 규칙을 둔다. 같은 앞 기록을 가진 기록끼리는 **서명 바이트의 해시가 사전순으로 작은 쪽**이 이긴다(git-bug 의 동점 규칙과 같다, 치우침이 없고 조작하기 어렵다). 시각이나 권한 순위로 고르면 시계 조작이나 상급자 쏠림이 생기므로 쓰지 않는다. 진 쪽은 버리지 않고 「승인됐지만 다시 얹어야 함」으로 남긴다. 진 기록의 승인자 앱이 다음에 켜질 때 새 줄기 위에 그 제안을 다시 합쳐 보고, 겹침이 없으면 새 기록을 자동 서명하고, 겹치면 제안을 승인 대기로 되돌린다. 자동 재서명은 승인자 본인 앱만 한다. 남의 승인을 대신 옮기면 서명의 뜻이 깨진다. 정직하게 말하면 이 규칙에서도 **두 사람이 잠시 다른 main 을 보는 일은 생긴다.** 서버가 없으므로 정본은 「서로 사본을 맞추면 같은 결론에 닿는다」(최종 수렴)이지 「누르는 순간 확정」이 아니다. 화면에는 「승인됨(아직 n 명만 확인)」처럼 잠정 상태를 보여 준다. 경쟁을 아예 없애고 싶으면 승인자를 한 명만 두면 되지만, 그러면 아래 열쇠 분실이 치명적이 된다.

**열쇠 분실**은 사람 단위 신원으로 다룬다. 열쇠는 앱 설치 단위이고 DPAPI 는 「이 PC 의 이 사용자」만 푼다([runner.rs:6](../../src-tauri/src/runner.rs)). PC 교체나 윈도 프로필 재설치에서 승인자가 사라진다. 명부에서 승인 권한은 사람에게 주고 기기 열쇠는 그 사람 아래 멤버로 둔다(Keyhive 모델). 한 기기를 잃으면 같은 사람의 다른 기기가 그 열쇠를 빼는 명부 판을 낸다. 모든 기기를 잃으면 다른 승인자 과반이 새 열쇠로 바꾸는 판을 낸다(Radicle 식 과반 revision). 그래서 **승인자는 최소 둘**을 권하고, 덱 만들 때 종이 복구 코드(두 번째 열쇠를 오프라인으로 뽑아 둔 것)를 하나 내주는 길을 둔다. 승인자가 한 명뿐인 덱에서 그 열쇠를 잃으면 줄기는 영영 못 움직이고, 남은 사람은 「줄기를 이어받은 새 덱」으로 갈라질 수밖에 없다. 이 경고는 명부 화면에 늘 띄운다.

## 야근 뒤 휴가 앞에서 남는 길은 서명된 묶음 파일이다

시나리오를 그대로 따라가면 결론이 분명하다. 밤늦게 승인까지 끝냈는데 다른 PC 가 모두 꺼져 있고, 이 PC 를 끄고 휴가를 가면 변경은 이 PC 안에 갇힌다. Windows 는 이것을 앱이 막게 두지 않는다. `SetThreadExecutionState` 는 유휴 잠자기만 막고 「사용자가 잠자기 · 덮개 닫기 · 전원 버튼을 쓰는 것은 막을 수 없다」고 문서가 못 박는다 ([SetThreadExecutionState](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate)). `PowerSetRequest` 의 요청도 사용자가 시작한 잠자기에서 끝나고, Modern Standby 배터리에서는 잠자기 시간 5분 뒤 끝난다 ([PowerSetRequest](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest)). Modern Standby 잠자기에서는 데스크톱 앱이 Desktop Activity Moderator 로 멈춘다 ([Modern Standby vs S3](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/modern-standby-vs-s3)). 종료는 `ShutdownBlockReasonCreate` 로 사유를 띄워 한 번 묻는 것까지만 되고, 보이는 창이 없는 앱은 종료를 취소할 수 없으며 「앱은 종료를 막을 수 있다고 기대하면 안 된다」 ([Shutdown changes](https://learn.microsoft.com/en-us/windows/win32/shutdown/shutdown-changes-for-windows-vista), [ShutdownBlockReasonCreate](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-shutdownblockreasoncreate)). Tauri 2 의 `WindowEvent` 에는 세션 종료 이벤트가 없어 HWND 를 서브클래싱해 `WM_QUERYENDSESSION` 을 직접 받아야 한다 ([tauri::WindowEvent](https://docs.rs/tauri/latest/tauri/enum.WindowEvent.html)). 깨우기 타이머 · Wake-on-LAN 은 완전히 끈 PC 를 못 깨우고 사무실 설정에 기대므로 믿을 수단이 아니다 ([KB973454](https://support.microsoft.com/en-us/kb/973454)).

그러니 전원 API 는 「잠깐 버티기와 경고」로만 쓰고, 넘기기는 파일로 한다. git bundle 은 바로 「서버 없이 git 객체를 오프라인으로 옮기는」 용도이고, 증분 묶음(`old..new`)과 `git bundle verify` 로 빠진 선행 커밋을 알려 주며 묶음을 원격처럼 fetch 할 수 있다 ([git-bundle](https://git-scm.com/docs/git-bundle)). ClaudePPT 의 묶음 파일은 **git bundle(제안 · 줄기 · 승인 기록 · 명부 ref) + 보낸 사람 서명 매니페스트**로 만든다. 받는 쪽은 온라인 fetch 와 똑같은 검증 경로를 거치므로, 누가 어떤 통로로 들고 오든 같은 결론이 난다. SSB 가 서명된 추가 전용 로그를 인터넷 · LAN · USB 로 똑같이 복제하고, 원 작성자 로그를 잃어도 팔로워 사본에서 복구한 선례가 이것이다 ([Wikipedia SSB](https://en.wikipedia.org/wiki/Secure_Scuttlebutt), [Tschudin ICN 2019](https://conferences2.sigcomm.org/acm-icn/2019/proceedings/icn19-19.pdf)). 지금의 `.cppt` 는 작업 트리까지 통째 zip 이라 큰 덱은 약 450MB 지만([project.rs:100-128](../../src-tauri/src/project.rs)), 증분 bundle 은 그날 바뀐 쪽 HTML 몇 KB 에 그친다.

통로는 이미 쓰는 것을 쓴다. 메신저에 파일을 붙이거나, OneDrive · 사내 SMB 공유를 우편함으로 쓴다. 공유 폴더는 「파일 하나를 여럿이 고치면」 충돌 사본과 Files On-Demand 자리 표시 문제로 깨진다 ([Obsidian 포럼](https://forum.obsidian.md/t/vault-synced-over-onedrive-across-multiple-machines-generates-many-copies-of-workspace-json/115229), [Obsidian Sync 안내](https://forum.obsidian.md/t/how-to-use-obsidian-sync-effectively-and-safely/80545)). 그래서 **보낸 사람 · 묶음마다 새 파일 이름(`outbox/<열쇠>/<순번>-<해시>.cpptb`)을 쓰고, 임시 이름으로 다 쓴 뒤 rename 하고, 한 번 쓴 파일은 다시 고치지 않는다.** 읽는 쪽은 모르는 파일만 가져오고 읽음 표시를 그 파일에 쓰지 않는다. Briar 가 「양쪽이 동시에 켜져 있어야 한다」는 도달성 문제를 사용자 소유 우편함 기기로 푼 것과 같은 생각이다 ([Briar Mailbox](https://briarproject.org/news/2023-briar-mailbox-released/)). 남는 PC 하나를 늘 켜 두는 「상시 피어」는 서버가 아니라 명부의 한 멤버일 뿐이므로, 원하는 팀에게만 선택지로 연다.

기회적 중계도 공짜로 따라온다. 서명된 기록은 누가 들고 와도 검증되므로, 오늘 밤 누군가 잠깐이라도 켜 있었다면 그 사람 사본이 다음 날 다른 사람에게 퍼뜨린다. 이 판단을 사용자가 할 수 있게 하는 열쇠는 **전달 상태 표시**다. 제안 · 승인마다 「이 PC 에만 있음」 → 「n 명에게 전달됨」 → 「모두에게 전달됨」 세 단계를 보이고, 수신 확인도 서명해 퍼뜨린다. 「이 PC 에만 있음」이 남아 있으면 창을 닫을 때 · 종료할 때 · 트레이에서 경고하고 바로 옆에 「파일로 보내기」를 둔다. 그동안만 AC 전원에서 상한(예: 2시간)을 둔 `PowerRequestSystemRequired` 를 켜고, 종료 때는 `WM_ENDSESSION` 5초 안에 묶음 파일을 우편함에 쓰는 것까지만 한다. 휴가 시나리오의 현실적 해답은 「끄기 전에 앱이 묶음 파일을 만들어 공유 폴더에 두거나 메신저로 보내라고 한 번 막아서 알려 준다」이다.

## 「담당 쪽만 보이기」는 사본을 주지 않는 사람에게만 남는다

전체 사본 구조와 부분 공개는 정면으로 부딪친다. 지금 이 기능은 「화면에서 감추는 것이 아니라 덱 주인 서버가 보내지 않는다」가 원칙이다. 맡지 않은 쪽은 자리만 남기고, `deck.json` · 남의 쪽 · 판 기록 · 지난 커밋 주소까지 막는다 ([README.md:176-182](../../README.md), [collab.rs:434-478](../../src-tauri/src/collab.rs), [collab.rs:1043-1048](../../src-tauri/src/collab.rs)). git 사본을 주면 모든 쪽의 전 이력이 넘어간다. 모두가 사본을 갖는 구조에서 부분 공개는 **암호화로만** 되고, 회수는 새 키로 **앞으로의 변경**만 막는다. Keyhive 는 데이터와 대칭키를 가진 사람은 그것을 읽을 수 있다고 한계를 명시하고 ([Keyhive notebook](https://www.inkandswitch.com/keyhive/notebook/)), git-crypt 는 한 번 준 접근의 회수를 지원하지 않으며 파일 이름 · 길이 · 변경 시점을 암호화하지 않는다 ([git-crypt README](https://github.com/AGWA/git-crypt)).

선택지는 셋이고 추천은 분명하다. 쪽 묶음별 대칭키를 받는 사람마다 감싸는 방식(age 수신자 모델)은 10명 이하 팀이면 비용 문제는 없지만, 암호문 쪽은 git diff · 3방향 합치기가 안 되고, 못 본 쪽을 승인할 수 없어 승인도 공개 범위로 나눠야 하며, 「숨은 쪽이 있다」는 사실과 크기는 새어 나간다. 이 설계 전체를 다시 한 번 짜는 수준의 일이고, 연구 단계인 BeeKEM 류 없이 동시 키 교체를 안전하게 풀기도 어렵다 ([Keyhive 02](https://www.inkandswitch.com/keyhive/notebook/02/)). 그래서 **담당 쪽만 볼 사람(외주 · 일부 쪽 기여자)은 사본을 주지 않고 지금의 호스트 모드로 계속 들인다.** 명부의 「보기 제한」 표시가 있는 사람에게는 git 전송을 열지 않고, 온라인인 아무 전체 사본 멤버가 지금의 `limit_view` · `Allow` 를 그대로 써서 그 사람에게 화면을 내준다. 그 사람의 쓰기는 의도 왕복 대신 「호스트가 대신 만든 제안」으로 들어간다. 브라우저 팀원도 git 사본을 못 쥐므로 같은 길로 들인다. 대가는 이 사람들이 호스트 모드의 한계(누군가 켜져 있어야 함)를 그대로 안는다는 점이다. 반면 **편집 범위 제한은 오히려 강해진다.** 담당이 서명된 명부에 들어가므로, 제안이 바꾼 파일이 작성자 담당 쪽 밖이면 모든 피어가 승인 검증에서 그 기록을 거절할 수 있다. 지금 화면 쪽 `scopeFor` · `fenceOf` 가 하던 일을 검증 규칙이 대신한다 ([collab.ts:322-342](../../src/lib/collab.ts), [store.ts:656-716](../../src/lib/store.ts)).

## 지금 코드로는 판 관리는 살리고 원격 계층은 걷는다

지금 구조는 목표와 데이터 소유 방향이 정반대다. 덱 주인 앱 안 127.0.0.1 서버가 store 의 JSON 투영을 밀어 주고, 쓰기는 「collab-intent」로 덱 주인 화면에 넘겨 최대 3시간 답을 기다리며, 팀원 PC 에는 덱 사본도 git 도 없다 ([collab.rs:13-14](../../src-tauri/src/collab.rs), [collab.rs:1199-1265](../../src-tauri/src/collab.rs)). iroh 열쇠는 주소로만 쓰이고 인증은 협업 서버의 링크 · 쿠키가 맡는다 ([p2p.rs:7-8](../../src-tauri/src/p2p.rs)). 목표에서는 열쇠의 쓰임이 「주소」에서 「신원」으로 바뀌고, 앱 팀원은 각자 main 창에서 자기 사본을 연다. 공유 덱 창(명령 권한 없는 외부 URL 웹뷰)이 필요 없어져 오히려 단순해진다.

먼저 막아야 할 기술 위험이 넷 있다. 첫째, **줄기를 바로 전진시키는 기존 경로들**이다. 판 남기기 `commit_all`, 되돌리기, 보류 「바꾸기」, 가지 넣기, 바깥 CLI 가 모두 덱 폴더의 `main` 을 바로 옮긴다([vcs.rs:146-166](../../src-tauri/src/vcs.rs), [vcs.rs:223-248](../../src-tauri/src/vcs.rs), [branch.rs:221-232](../../src-tauri/src/branch.rs)). 「덱 폴더 = 줄기 체크아웃」 전제([branch.rs:27-30](../../src-tauri/src/branch.rs))를 「덱 폴더 = 내 작업 갈래 체크아웃」으로 바꾸고, 줄기는 승인 경로만 움직이게 해야 한다. 하나라도 남으면 검증 안 된 줄기가 생겨 남들이 거절하고 갈라진다. 받는 쪽 검증을 최종 방어선으로 두는 까닭이다. 둘째, **`deck.json` 겹침**이다. 쪽 순서의 유일한 정본이고 저장할 때마다 `updated` 시각을 고치므로([deck.ts:69](../../src/lib/deck.ts)) 쪽을 하나씩 더한 두 제안도 거의 늘 겹친다. `updated` 를 판에서 빼고(커밋 시각으로 대신) 쪽 id 집합 · 순서를 3방향으로 합치는 전용 합치기를 두어야 승인 관문이 겹침으로 막히지 않는다. 셋째, **남이 쓴 쪽 HTML 이 명령 권한이 있는 내 main 창에서 열린다.** 지금 main 창의 `deck://` 내용은 내가 쓴 것이었다. 원격 경로의 sandbox iframe · CSP `connect-src 'none'`([collab.rs:5-8](../../src-tauri/src/collab.rs))이 `deck://` 에도 같은 강도로 걸리는지는 확인하지 못했고, 1단계 전에 반드시 확인한다. 넷째, 원격 pack 을 내 저장소에 넣으므로 크기 한도 · ref 이름 검사(`plain()`, [vcs.rs:250-252](../../src-tauri/src/vcs.rs)) · 격리 ref 가 필요하다.

작업량은 코드 조사 노트의 영역별 추정을 따른다(줄 수는 추정이고 화면 tsx 의 원격 분기는 세지 않았다).

시험은 vcs.rs 8개 · branch.rs 3개가 대부분 남고(「덱 폴더 = 줄기」 전제의 `sian_is_a_deck_that_merges_back` 은 고친다), invite.rs 9개와 runner.rs 5개(`dpapi_round_trip` 만 남김), collab.rs 의 세션 묶음 · 의도 시험 8개는 뜻이 바뀌거나 걷힌다. 새로 쓸 시험은 서명 위조, 승인 권한 없는 열쇠, 줄기 되감기, 기록 재생, 박탈 뒤 서명, 동시 승인 승자 결정, 묶음 파일 변조, 이력 안 이어진 사본, `deck.json` 동시 쪽 추가다 (시험 목록은 [collab.rs:1636-1807](../../src-tauri/src/collab.rs), [invite.rs:242-375](../../src-tauri/src/invite.rs), [vcs.rs:516-592](../../src-tauri/src/vcs.rs)).

추천 단계는 다섯이다. 각 단계는 앞 단계 없이도 쓸모가 있게 짰다. **1단계(기초, 네트워크 없음)**: `deck://` sandbox 확인, `deck.json` 의 `updated` 빼기와 전용 합치기, 명부 체인 · 승인 기록 체인 · 검증 모듈과 그 시험. 덱 폴더를 「내 작업 갈래」로 바꾸고 줄기 직접 전진 경로를 승인 경로로 모은다. 혼자 쓰는 덱에서는 창세 열쇠가 곧 유일한 승인자라 사용자 체감이 거의 없다. **2단계(파일로 협업)**: 서명된 증분 묶음 파일 내보내기 · 들이기와 공유 폴더 우편함, 전달 상태 표시. 아직 iroh 전송이 없어도 이 단계만으로 「모두 사본 · 승인 게이트」가 메신저와 공유 폴더 위에서 돈다. 야근 뒤 휴가 시나리오가 여기서 풀린다. **3단계(iroh 전송)**: `claudeppt/git/1` fetch 전용 upload-pack, 명부 열쇠로 피어 찾기, 격리 ref 와 상한, 끄기 전 경고와 전원 요청. **4단계(걷기)**: 앱 팀원용 투영 · 의도 · 러너 계층을 걷고, 호스트 모드는 보기 제한 멤버 · 브라우저 팀원 창구로 줄인다. 공유 Claude 세션은 사라지고 Claude 는 각자 자기 사본에서 돈다. **5단계(선택)**: gossip 알림, 상시 피어, 유료 릴레이 설정. 쪽 단위 암호화는 이 로드맵에 넣지 않는다.

## Conclusion

이 전환의 본질은 전송이 아니라 신원이다. iroh 위 git 은 `pipe` 를 한 번 더 쓰는 수준이고 판 관리는 이미 있다. 진짜 새로 생기는 것은 「누가 승인자인가」를 서버 없이 모두가 같은 답으로 계산하는 명부와, 그 답이 바뀌는 순간(박탈 · 분실 · 동시 승인)의 규칙이다. 그래서 순서도 전송보다 서명 · 명부 · 검증을 먼저 둔다. 검증이 단단하면 통로는 iroh 든 메신저 파일이든 공유 폴더든 상관없어지고, 「아무도 켜져 있지 않을 때」라는 문제는 기술 문제에서 「끄기 전에 파일 하나를 보내게 하는」 UX 문제로 바뀐다. 이 점 때문에 2단계(파일로 협업)를 3단계(iroh 전송)보다 앞에 두는 것이 이 팀의 실제 고통에 가장 빨리 닿는 길이다.

동시에 이 설계는 두 가지를 솔직하게 내려놓는다. 정본은 「누르는 순간 확정」이 아니라 「사본을 맞추면 수렴」이 되고, 한 번 준 사본은 되돌릴 수 없다. 앞의 것은 잠정 상태 표시로, 뒤의 것은 보기 제한 멤버를 호스트 모드에 남기는 혼합 구조로 감당한다. 지금의 호스트 모드를 버리는 것이 아니라 「사본을 줄 수 없는 사람의 창구」로 좁혀 살리는 것이 이 설계를 현실적으로 만드는 마지막 조각이다.
