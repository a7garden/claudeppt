# 분산 협업 1단계: 서명한 명부와 승인 기록으로 줄기를 지킨다

2026.11.27 초안. 근거와 다른 길을 버린 까닭은 같은 폴더 「조사 보고서.md」와 `조사/` 의 노트 넷에 있다.

> **구현하며 바꾼 것 (2026.11.27, `src-tauri/src/trust.rs`)** 아래 본문보다 이것이 앞선다.
> - **사슬은 하나다.** 명부 판과 승인 기록을 `refs/cppt/chain` 한 사슬에 차례로 쌓는다(칸마다 `kind: roster | approve`). 둘을 나누면 「권한을 뺀 판」과 「그 사람의 승인」의 앞뒤를 가릴 수 없어, 5절 「권한을 뺄 때」의 `trunk` 칸으로도 이미 들어간 승인이 거꾸로 무효가 되는 틈이 남았다. 한 사슬이면 지금 명부는 늘 「바로 앞까지의 마지막 명부 칸」이다.
> - **1단계에서 덱 폴더는 그대로 `main` 을 연다(9절은 2단계로 미룬다).** 줄기를 옮기는 명령이 끝날 때마다 사슬이 줄기를 따라 봉한다(`seal`). 1단계에서는 명부에 이 PC 의 열쇠 하나뿐이라 결과가 같고, `cppt/mine` 으로 바꾸는 큰 변경을 승인자가 아닌 사람이 생기는 2단계로 미뤘다. 앱 밖 git 으로 줄기를 되감은 덱은 승인자가 `rewind` 표시를 단 승인으로 봉한다.
> - **승인은 `base` 가 `head` 의 조상이면 된다.** 첫 부모일 필요는 없다. 판 여러 개를 한 승인으로 봉할 수 있다.
> - **갈래 고르기 1번 규칙을 더했다.** 한쪽 갈래가 승인 권한을 뺀 열쇠는 다른 쪽 갈래에서 그 열쇠가 서명한 칸부터 잘라 낸 뒤 해시를 견준다. 해시만 견주면 권한을 잃은 사람이 박탈 전 자리에서 해시가 작은 칸을 골라 낼 때까지 서명을 되풀이해 이길 수 있다.
> - **「사본에서 가져오기」는 1단계에서 견주기만 한다.** 사본의 사슬을 `refs/cppt/peers/copy-<id>/` 에 받아 검증하고 이 덱의 것과 견준 결과(같음 · 앞섬 · 뒤짐 · 갈라짐 · 다른 덱 · 맞지 않음)를 알린다. 줄기는 옮기지 않는다. 사본을 만들 때 사슬도 함께 떼어 가 같은 덱 id 를 잇는다.
> - **슬라이드 sandbox 는 늘 건다(11절).** 남이 쓴 쪽이 있든 없든 무대 · 화면 밖 굽기 · 처음 화면 미리보기 모두. Edge 로 sandbox 안 굽기가 그대로 되는 것을 확인했고, 막히는 sessionStorage(고친 요소 다시 고르기)는 앱 화면이 맡는다.
> - 명부 화면은 변경 기록 창 위의 한 줄이다(`Trust.tsx`): 승인자 · 복구 열쇠 경고 · 내 이름 고치기 · 복구 열쇠 만들기 · 복구 열쇠로 되찾기.

## 1. 무엇을 바꾸나

목표 전체: 모두가 덱 전체 사본을 갖고, 승인 권한을 가진 사람이 서명한 변경만 줄기(`main`)에 들어간다. 늘 켜진 서버는 두지 않는다.

1단계는 그 바닥만 놓는다. **네트워크를 건드리지 않는다.** 한 PC 안에서 다음이 서야 한다.

- 덱마다 서명한 명부(누가 어떤 권한인가)가 있다.
- 줄기는 서명한 승인 기록을 따라서만 움직인다. 줄기를 바로 옮기던 길은 모두 승인 경로로 모인다.
- 받은 저장소(지금은 「사본에서 가져오기」 · `.cppt`)의 줄기와 명부를 검증하고, 맞지 않으면 받지 않는다.
- 두 사람이 쪽을 하나씩 더한 정도로는 겹치지 않는다(`deck.json` 합치기).
- 남이 쓴 쪽 HTML 이 내 창에서 돌아도 앱에 손대지 못한다.

혼자 쓰는 덱에서는 달라 보이는 것이 없어야 한다. 덱을 만든 사람이 유일한 승인자이고 자기 변경은 저절로 승인되므로, 지금처럼 고치면 바로 줄기에 들어간다.

## 2. 이번 단계에서 하지 않는 것

- iroh 위 git 주고받기, 피어 찾기, 전달 상태: 3단계.
- 서명한 묶음 파일 · 공유 폴더 우편함 · 끄기 전 경고: 2단계.
- 지금 공유(덱 주인이 화면을 내주는 방식)는 그대로 둔다. 걷는 것은 4단계다. 1단계 동안 공유로 들어온 팀원의 변경은 지금처럼 덱 주인 앱에서 일어나므로, 덱 주인의 자동 승인으로 줄기에 들어간다.
- 쪽 단위 암호화: 로드맵에 없다.

## 3. 정한 것

앞의 대화에서 열어 둔 물음에 아래처럼 정하고 간다. 바꾸려면 이 절을 고친다.

| 물음 | 정한 것 | 까닭 |
|---|---|---|
| 승인자 | 명부에서 「승인」 권한을 가진 사람 | 사용자 결정 |
| 승인자 자신의 변경 | 스스로 승인할 수 있다. 덱 설정 「다른 승인자 확인 받기」를 켜면 막는다 | 혼자 쓰는 덱 · 작은 팀이 승인 단추에 막히지 않게 |
| 승인 전 제안을 누가 보나 | 사본을 가진 모두 | 사본이 퍼지는 순간 숨길 수 없다. 숨기는 척하지 않는다 |
| 「담당 쪽만 보이기」 | 그 사람은 사본을 받지 않고 지금 공유 방식으로 들어온다(혼합 구조) | 전체 사본으로는 지킬 수 없다 |
| 브라우저 팀원 | 위와 같은 길로 남긴다 | 브라우저는 사본을 쥘 수 없다 |
| 승인할 수 있는 수 | 승인자 한 명의 서명이면 된다(threshold 1) | 작은 팀. 늘리는 것은 명부의 값 하나로 열어 둔다 |
| 명부를 바꾸는 수 | 지금 승인자의 과반 | Radicle 과 같다. 한 사람이 혼자 남을 내쫓지 못하게 |

## 4. 저장소 안 자리

줄기 밖 ref 셋을 더한다. 모두 git 커밋 사슬이고, 커밋 안에는 작은 JSON 파일 하나만 둔다.

| ref | 담는 것 | 누가 옮기나 |
|---|---|---|
| `refs/cppt/roster` | 명부 판의 사슬 | 승인자 과반 서명이 모인 판만 |
| `refs/cppt/trunk` | 승인 기록의 사슬 | 승인자 서명이 붙은 기록만 |
| `refs/cppt/proposals/<작성자 열쇠>/<id>` | 제안 하나(지금의 가지 · 보류와 같은 갈래) | 작성자 |

- `main` 은 `refs/cppt/trunk` 마지막 기록이 가리키는 커밋으로만 맞춘다. 맞추는 것은 fast-forward 뿐이다. 앱이 `main` 을 직접 옮기는 곳은 이 맞추기 하나만 남긴다.
- git 내장 서명은 쓰지 않는다. `commit.gpgsign=false` · `log.showSignature=false` 는 그대로 둔다(`vcs.rs:29-36`, 판 목록 파서가 기대고 있다).
- 3단계에서 남에게서 받은 ref 는 `refs/cppt/peers/<열쇠>/…` 에 먼저 받고, 검증을 지난 것만 위 셋으로 옮긴다. 1단계의 「사본에서 가져오기」도 같은 격리 자리를 쓴다.

## 5. 명부

### 판 하나의 꼴

```json
{
  "v": 1,
  "deck": "<창세 판 해시>",
  "seq": 3,
  "prev": "<앞 판 해시 | null>",
  "trunk": "<이 판을 낼 때의 줄기 커밋>",
  "people": [
    { "id": "p1", "name": "이정원", "keys": ["<z32 열쇠>", "<z32 열쇠>"],
      "role": "approve", "slides": [], "replica": true }
  ],
  "approve": 1,
  "sigs": [ { "key": "<z32>", "sig": "<base64>" } ]
}
```

- `role`: `approve` · `edit` · `assigned` · `comment` · `view`. 지금 `invite.rs` 의 `Role` 넷에 `approve` 를 더한 것이다. `approve` 는 `edit` 를 품는다.
- `slides`: `assigned` 일 때 맡은 쪽 id. 지금 판 밖 `.claudeppt/assign.json` 에 있던 담당표가 여기로 온다. 담당이 이제 검증의 입력이기 때문이다.
- `replica`: 사본을 받는 사람인가. `false` 면 3단계에서 git 전송을 열지 않고 지금 공유 방식으로만 들인다(3절).
- `keys`: 한 사람 아래 기기 열쇠 여럿. 열쇠는 앱마다 있는 `p2p.key` 의 공개 열쇠다(`p2p.rs:45-62`). 이름은 표시용일 뿐 아무것도 보증하지 않는다. 지금 「같은 이름이면 권한을 잇는다」(`invite.rs:151-163`)는 명부에서 쓰지 않는다.
- `trunk`: 이 판을 낼 때 줄기가 있던 커밋. 권한을 뺀 판이 어느 승인 기록보다 앞서는지 가리는 데 쓴다(7절).
- `deck`: 창세 판의 해시를 덱 id 로 쓴다. 덱 폴더 이름 · 경로가 바뀌어도 같은 덱이다.

### 서명

- 서명할 바이트는 `"claudeppt/roster/1\n"` + 정규 JSON(`sigs` 를 뺀 판, 키 정렬 · 공백 없음)이다. 머리 글은 같은 열쇠로 한 다른 서명(승인 기록 등)과 섞이지 않게 한다.
- 서명은 iroh-base 1.5 의 `SecretKey::sign` 과 `PublicKey::verify` 로 한다(iroh-base `src/key.rs:323` · `:134`). 새 암호 라이브러리는 들이지 않는다.
- 판 해시는 서명할 바이트의 SHA-256 이다. 서명은 해시에 넣지 않는다(서명이 더 모여도 판은 같다).

### 효력

- 창세 판(`seq` 0)은 덱을 만든 열쇠 하나의 서명으로 선다.
- 그 뒤 판은 `prev` 가 지금 판이어야 하고, **지금 판**의 승인자 과반 서명이 모여야 선다. 새 판의 승인자가 아니라 지금 판의 승인자가 센다.
- 한 판이 서면 같은 `prev` 를 가진 다른 판은 모두 낡음이 된다. 다시 하려면 새 판 위에서 다시 낸다.
- 서명이 모자란 판은 `refs/cppt/roster-pending/<해시>` 에 두고 서명을 더 모은다. 1단계에서는 승인자가 한 명인 덱이 대부분이라 바로 선다.

### 권한을 뺄 때

- 사람을 빼거나 승인 권한을 내리는 것도 새 판이다.
- 승인 기록은 자기가 기댄 명부 판 해시를 담는다(6절). 그 판이 기록을 낸 때의 지금 판이 아니면 무효다(7절).
- 남는 구멍: 빠진 사람이 박탈 판을 아직 못 받은 척하며 옛 판에 기대 서명할 수 있다. 7절의 규칙으로 박탈 판보다 뒤에 쌓인 그 사람 기록은 거절하지만, 박탈 판과 동시에 갈라진 기록 한두 건은 들어갈 수 있다. 이 한계를 명부 화면 도움말에 적는다.
- 이미 준 사본은 회수할 수 없다. 내보내기는 「앞으로의 줄기를 주지 않는다」는 뜻이다.

### 열쇠를 잃을 때

- 기기 하나를 잃으면 같은 사람의 다른 기기가 그 열쇠를 빼는 판을 낸다.
- 모든 기기를 잃으면 다른 승인자 과반이 새 열쇠로 바꾸는 판을 낸다.
- 승인자가 한 명뿐인 덱은 그 열쇠를 잃으면 줄기가 멈춘다. 덱을 만들 때 **복구 열쇠**를 하나 더 만들어 같은 사람의 두 번째 열쇠로 명부에 넣고, 그 비밀을 한 번만 보여 준다(종이 · 비밀번호 관리자에 두라고). 복구 열쇠로 들어오면 그 PC 의 앱 열쇠를 더하는 판을 낸다.
- 명부 화면에 승인자가 한 명이고 복구 열쇠도 없으면 경고를 늘 띄운다.

## 6. 승인 기록

```json
{
  "v": 1,
  "deck": "<덱 id>",
  "n": 42,
  "prev": "<앞 기록 해시 | null>",
  "base": "<앞 줄기 커밋>",
  "head": "<새 줄기 커밋>",
  "tree": "<새 줄기 커밋의 트리 해시>",
  "proposal": { "by": "<작성자 열쇠>", "id": "<제안 id>", "tip": "<제안 끝 커밋>" },
  "roster": "<기댄 명부 판 해시>",
  "key": "<승인자 열쇠>",
  "at": "2026-11-27T22:40:00+09:00",
  "sig": "<base64>"
}
```

- 서명할 바이트는 `"claudeppt/approval/1\n"` + 정규 JSON(`sig` 를 뺀 것).
- `head` 는 `base` 를 첫 부모로 둔 커밋이어야 한다. 제안을 합친 커밋이거나(합치기), `base` 위에 바로 쌓인 제안 커밋(fast-forward)이다.
- `tree` 를 따로 묶는 까닭: 커밋 해시는 SHA-1 이다. 트리 해시까지 맞춰 보면 같은 커밋 해시로 다른 내용을 내미는 공격의 문턱이 오른다. git 의 SHA-256 저장소로 옮기는 것은 이 단계에서 하지 않는다.
- `at` 은 화면 표시용이다. 순서와 승자 결정에 쓰지 않는다(8절).
- 창세 기록(`n` 0)은 덱을 옮길 때의 줄기 끝을 `head` 로, 창세 명부를 `roster` 로 둔다(12절).

## 7. 검증

받는 쪽이 하는 일이다. 내 앱이 만든 기록도 같은 함수를 지난 뒤에야 줄기를 옮긴다. 검증하는 길은 하나만 둔다.

1. 명부 사슬을 창세 판부터 따라간다. 판마다 `prev` · `seq` 이어짐, 서명 · 과반을 본다. 어긋난 판에서 멈추고 그 앞까지만 믿는다.
2. 승인 기록 사슬을 창세 기록부터 따라간다. 기록마다 아래를 본다.
   - `prev` 가 앞 기록의 해시이고 `n` 이 하나씩 늘어난다.
   - `base` 가 앞 기록의 `head` 다.
   - `head` 커밋이 저장소에 있고, 첫 부모가 `base` 이며, 트리가 `tree` 다.
   - `key` 가 `roster` 판에서 승인 권한을 가진 사람의 열쇠다.
   - `roster` 판이 이 기록 시점의 지금 판이다. 「이 기록 시점」은 1번에서 얻은 명부 사슬 중 이 기록보다 인과적으로 앞선 마지막 판이다. 명부 판은 그 판을 낸 때의 줄기 커밋(`trunk`)을 담는다. 박탈 판의 `trunk` 가 이 기록의 `base` 와 같거나 앞서면, 박탈 전 판에 기댄 이 기록은 무효다.
   - 「담당 쪽만」 작성자의 제안이면 `base..head` 에서 바뀐 파일이 그 사람의 `slides` 와 공통 파일(테마 · `assets/`) 안이다. 덱 설정 「다른 승인자 확인 받기」가 켜져 있으면 `key` 의 사람이 `proposal.by` 의 사람과 다르다.
   - 서명이 맞다.
3. 어긋난 기록에서 멈추고 그 앞까지를 줄기로 삼는다. 어긋난 기록과 그 뒤는 버리지 않고 `refs/cppt/rejected/<해시>` 에 두고 까닭을 남긴다(무엇이 어긋났는지 사람이 볼 수 있게).
4. `main` 을 마지막 기록의 `head` 로 fast-forward 한다. fast-forward 가 아니면 옮기지 않고 알린다. 이 경우는 내 앱이 줄기를 몰래 옮긴 것이니 버그다.

검증은 매번 처음부터 하지 않는다. 마지막으로 믿은 기록 해시를 앱 데이터에 두고 그 뒤만 본다. 앱 데이터가 없어지면 처음부터 다시 한다.

## 8. 동시 승인

승인자 둘이 같은 줄기 위에서 서로 다른 제안을 승인하면 같은 `prev` 의 기록이 둘 생긴다. 1단계에서는 같은 PC 에서 두 기록이 생길 일이 없지만, 「사본에서 가져오기」로 들어올 수 있으므로 규칙을 지금 정해 둔다.

- 같은 `prev` 의 기록끼리는 **서명 바이트의 SHA-256 이 사전순으로 작은 쪽**이 이긴다. 시각이나 권한 순위로 고르지 않는다(시계를 속이거나 상급자 쪽으로 쏠린다).
- 진 기록은 `refs/cppt/lost/<해시>` 에 둔다. 진 기록을 낸 승인자의 앱만 그것을 다시 다룬다.
  - 그 제안을 새 줄기 위에 다시 합쳐 보고, 겹치지 않으면 새 기록을 자기 열쇠로 다시 서명한다.
  - 겹치면 제안을 「승인 대기」로 되돌리고 알린다.
- 남의 승인을 대신 다시 서명하지 않는다. 서명이 그 사람의 판단이라는 뜻이 깨진다.
- 이 규칙에서도 두 사람이 잠시 다른 줄기를 보는 일은 생긴다. 사본을 맞추면 같은 결론에 닿는다. 화면에는 지나치게 확정된 말을 쓰지 않는다(13절).

## 9. 덱 폴더와 줄기

지금은 덱 폴더가 줄기 체크아웃이라(`branch.rs:27-30`) 판 남기기가 곧 줄기 전진이다. 이것을 바꾼다.

- 덱 폴더는 **내 작업 줄** `cppt/mine` 을 체크아웃한다. 손 편집 · Claude 턴 · 되돌리기 · 보류 「이것으로 바꾸기」 · 가지 넣기는 모두 `cppt/mine` 에 쌓인다.
- 「승인」은 `cppt/mine`(또는 남의 제안)을 줄기에 넣는 일이다. 지금 `merge_into`(`branch.rs:183-219`)로 합치고, 겹치면 지금처럼 줄기는 그대로 두고 겹친 파일을 알린다. 합친 결과에 승인 기록을 붙여 7절 검증을 지나면 `main` 을 옮긴다.
- **자동 승인**: 내가 승인자이고 「다른 승인자 확인 받기」가 꺼져 있으면, `cppt/mine` 에 변경이 쌓일 때마다 앱이 바로 승인한다. 혼자 쓰는 덱은 이 때문에 지금과 똑같이 보인다. 줄기와 내 작업 줄은 늘 같은 커밋에 있다.
- 승인자가 아니면 `cppt/mine` 이 곧 내 제안이다. 「제안하기」를 누르면 `refs/cppt/proposals/<내 열쇠>/<id>` 로 굳힌다.
- 판(릴리즈) 태그 `r<k>` 는 줄기 커밋에만 단다. 줄기 밖 커밋으로 판을 내려 하면 먼저 승인하라고 알린다.

줄기를 바로 옮기던 길과 바꿀 곳:

| 지금 | 어디 | 바꾼 뒤 |
|---|---|---|
| 판 남기기 `vcs_commit` · `commit_all` | `vcs.rs:91` · `:146-166` | `cppt/mine` 에 쌓고, 자동 승인이면 승인 |
| 되돌리기 `vcs_restore` | `vcs.rs:223-248` · CLI `cli.rs:514` | 같다 |
| 턴 얹기 `vcs_work_finish` · `land` | `vcs.rs:342-388` | 얹는 곳이 덱 폴더라 그대로 `cppt/mine` 에 쌓인다 |
| 보류 다시 넣기 · 바꾸기 | `vcs.rs:418-446` | 같다 |
| 가지 넣기 `vcs_sian_merge` | `branch.rs:222` | 가지를 `cppt/mine` 에 넣는다. 줄기에 바로 넣지 않는다 |
| 줄기 받기 `vcs_sian_update` | `branch.rs:235` | 받는 곳을 `main` 으로 둔다(바뀌지 않음) |
| 사본에서 가져오기 `vcs_fork_fetch` | `branch.rs:390` | 격리 ref 에 받고 7절 검증. 명부 · 기록이 없는 옛 사본은 지금처럼 가지로만 받는다 |
| CLI `commit` · `restore` | `cli.rs:126` · `:514` | 같은 함수를 부르므로 따라온다. 「줄기를 바로 옮기는 CLI 명령」은 남기지 않는다 |
| 판 태그 `vcs_tag` | `vcs.rs:214` | 줄기 커밋인지 본다 |

`main` 을 쓰는 곳이 위 맞추기 하나뿐인지는 시험으로 지킨다(14절, `main` 을 바꾸는 git 인자를 모두 grep 하는 시험).

## 10. `deck.json` 합치기

`deck.json` 은 쪽 순서의 유일한 정본이고, 저장할 때마다 `updated` 를 고친다(`deck.ts:69`). 그대로 두면 쪽을 하나씩 더한 두 제안도 늘 겹친다.

- `updated` 를 파일에서 뺀다. 보일 곳이 있으면 마지막 줄기 커밋 시각을 쓴다. 옛 파일에 남은 `updated` 는 읽을 때 무시한다.
- `deck.json` 전용 합치기를 git 합치기 드라이버로 단다.
  - 덱의 `.gitattributes` 에 `deck.json merge=cpptdeck` 를 둔다(덱을 만들 때 · 옮길 때 쓴다).
  - 드라이버 명령은 `git()` 의 `-c merge.cpptdeck.driver=…` 로 매번 준다. 사용자 git 설정에 의존하지 않고, 앱 밖 git 으로 합치면 보통 줄 합치기로 돌아간다.
  - 드라이버는 같은 실행 파일의 CLI 하위 명령 `claudeppt.exe merge-deck %O %A %B` 다.
- 합치는 규칙(세 판: 바탕 O, 내 것 A, 남의 것 B):
  - 쪽 목록은 id 집합으로 본다. 한쪽만 더한 쪽은 들어가고, 한쪽만 뺀 쪽은 빠진다.
  - 순서는 A 의 순서를 바탕으로 B 가 더한 쪽을 B 에서 앞에 있던 쪽 바로 뒤에 넣는다. 둘 다 같은 쪽을 다른 자리로 옮겼으면 A 를 따르고 겹침으로 알린다.
  - 쪽 하나의 칸(`title` · `notes` · `hidden`)은 칸마다 3방향으로 본다. 둘이 같은 칸을 다르게 바꾸면 겹침이다.
  - 덱 칸(`title` · 크기 · `theme` · `page`)도 칸마다 같다.
  - 한쪽이 지운 쪽을 다른 쪽이 고쳤으면 겹침이다.
- 겹침이면 드라이버가 실패를 돌려주고 지금의 겹침 처리(보류 · 알림)를 그대로 탄다.

## 11. 슬라이드 격리

지금 내 창의 슬라이드 iframe 에는 sandbox 가 없다. 원격 화면에서만 `allow-scripts` 로 다른 출처를 만든다(`Workspace.tsx:62`). 내 창의 슬라이드는 내가(내 Claude 가) 쓴 것이라는 전제였다. 분산 구조에서는 남이 쓴 쪽 HTML 이 명령 권한이 있는 내 main 창 안에서 돈다.

- 1단계에서 확인할 것: sandbox 없는 `deck://` iframe 의 스크립트가 Tauri IPC(`__TAURI_INTERNALS__` · `ipc://`)에 닿는가. 닿지 않더라도 아래는 한다.
- 남이 쓴 커밋이 하나라도 들어온 덱(명부에 나 아닌 사람이 있는 덱)은 슬라이드 iframe 을 늘 `sandbox="allow-scripts"` 로 연다.
  - 직접 편집 · 런타임(`rt.js`)이 부모와 주고받는 길이 `postMessage` 만인지 먼저 본다. `contentWindow` 의 속을 직접 만지는 곳이 있으면 `postMessage` 로 바꾼다.
- `deck://` 응답의 CSP(`lib.rs:208`)는 그대로 둔다. 지금 CSP 는 `connect-src 'self' data: blob:` 이라 슬라이드가 자기 덱 밖으로 요청을 보내지는 못한다.

## 12. 지금 덱 옮기기

- 덱을 열 때 `refs/cppt/roster` 가 없으면 옮긴다.
  1. 이 앱의 열쇠로 창세 명부를 만든다. 사람은 나 하나, 권한은 `approve`.
  2. 지금 `main` 끝을 `head` 로 둔 창세 승인 기록을 만든다.
  3. 덱 폴더를 `cppt/mine` 으로 바꿔 체크아웃한다(같은 커밋이라 파일은 그대로다).
  4. `.gitattributes` 에 `deck.json` 합치기를 더하고 판으로 남긴다.
- 지금 공유에 쓰는 장부(`collab/<덱 지문>.json`)의 권한 · 담당은 1단계에서 명부로 옮기지 않는다. 장부의 사람에게는 아직 열쇠가 없다(쿠키뿐이다). 3단계에서 팀원이 사본으로 들어올 때 열쇠를 받아 명부에 넣는다. 그때까지 담당표는 두 곳에 있으니, 1단계에서는 장부 쪽을 따른다.
- 옮긴 덱을 옛 앱(0.15 이하)이 열면 `cppt/mine` 이 보이고 `main` 은 그대로라 깨지지는 않는다. 옛 앱이 `cppt/mine` 위에 판을 남기면 새 앱이 다음에 열 때 자동 승인한다.

## 13. 화면

1단계에서 새로 보이는 것은 적다.

- 제목 줄 「공유」 창 옆에 「명부」: 사람 · 열쇠 · 권한 · 담당 쪽 · 복구 열쇠 경고. 1단계에서는 보기와 내 이름 고치기, 복구 열쇠 만들기만 된다.
- 변경 기록 그래프: 줄기 점에 승인한 사람을 보인다. 버려진 기록(`rejected`) · 진 기록(`lost`)이 있으면 그래프 위에 한 줄로 알린다.
- 승인자가 아닌 사람의 화면(3단계부터 실제로 생긴다)에 쓸 말은 지금 정한다: 「내 변경 · 아직 줄기에 없음」 · 「승인 대기」 · 「승인됨」. 「확정」이라는 말은 쓰지 않는다(8절).
- 자동 승인 덱에서는 아무것도 바뀌어 보이지 않아야 한다.

## 14. 시험

새로 쓰는 것:

- 명부: 창세 판 서명 · 과반 모자란 판은 서지 않음 · 낡은 `prev` 판은 낡음 · 서명 위조 · 사람 여러 열쇠 · 복구 열쇠로 열쇠 더하기.
- 승인 기록: 위조 서명 · 승인 권한 없는 열쇠 · 되감기(`base` 가 앞 `head` 가 아님) · 재생(같은 기록을 다른 덱에) · `tree` 불일치 · 박탈 판 뒤의 서명 · 「담당 쪽만」 작성자의 범위 밖 파일 · 「다른 승인자 확인 받기」에서 자기 승인.
- 동시 승인: 같은 `prev` 두 기록에서 모든 순서로 넣어도 같은 승자 · 진 쪽 다시 서명 · 겹치면 승인 대기.
- 줄기 지키기: 판 남기기 · 되돌리기 · 보류 · 가지 넣기 · CLI 가 `main` 을 옮기지 않음 · `main` 을 쓰는 git 호출이 맞추기 함수 하나뿐(소스 grep).
- `deck.json`: 쪽 하나씩 더하기 · 한쪽 지우기와 다른 쪽 고치기 · 같은 쪽 다른 자리 · 칸 단위 겹침 · 앱 밖 git 에서는 줄 합치기로 돌아감.
- 옮기기: 옛 덱을 열면 명부 · 창세 기록이 생기고 파일이 그대로 · 옛 앱이 남긴 판을 자동 승인.
- 사본에서 가져오기: 명부가 다른 덱(다른 창세)은 거절 · 검증이 어긋난 기록은 `rejected` 로.

고치는 것: `branch.rs` 의 `sian_is_a_deck_that_merges_back`(덱 폴더 = 줄기 전제). 그 밖의 `vcs.rs` 8개 · `branch.rs` 나머지는 그대로 지나야 한다. `invite.rs` · `collab.rs` · `runner.rs` 시험은 1단계에서 건드리지 않는다.

## 15. 남은 물음

1단계를 시작하는 데 막히는 것은 없다. 아래는 하면서 정한다.

- 정규 JSON 규칙: RFC 8785(JCS)를 따를지, 키 정렬 · 공백 없음 · 문자열 그대로의 간단한 규칙으로 갈지. 숫자는 정수만 쓰니 간단한 규칙으로도 충분해 보인다.
- 「담당 쪽만」 검증에서 「공통 파일」의 범위: 테마 · `assets/` 말고 `deck.json` 의 자기 쪽 칸 고치기를 허용하는 방법(10절의 칸 단위 합치기를 재사용).
- 복구 열쇠를 보여 주는 꼴: 글자 열(z32) 그대로인지, 단어 목록으로 바꿀지.
- 11절 확인 결과에 따라 혼자 쓰는 덱에도 sandbox 를 늘 걸지.
